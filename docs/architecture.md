# 構成とレイヤーの責務

- 各リポジトリでは、必要なレイヤーをこの配置・命名にそろえます。

| 配置 | 責務 | レイヤー間の参照先 |
| --- | --- | --- |
| `src/domain/` | モデル、純粋な業務判断・生成、Repositoryの契約 | Domain |
| `src/application/` | 状態の取得、ドメイン操作、保存の組み立て | Application・Domain |
| `src/infrastructure/` | Repositoryの実装、DB・外部APIの操作とモデルへの変換 | Infrastructure・Domain |
| `src/presentation/` | 入力、HTTP応答、画面 | Presentation・Application・Domain |
| Workerの入口 | binding・設定の取得と具体実装の組み立て | 必要な各レイヤー |

- 開発用スクリプトは`scripts/`、結合テストなどは`test/`、Vitestの設定は`vitest.config.ts`に置きます。
- 単体テストは各レイヤー内の`*.test.ts`・`*.test.tsx`にも配置できます。

## 業務の表現と依存

- モデルの境界は業務上の責務で決めます。
  - 同時保存が必要なことだけを理由に、独立したモデルをまとめたり、操作用モデルを増やしたりしません。
- 別集約はIDで参照します。
- Applicationの依存はオブジェクトの引数で受け取り、操作の入力と分けます。
- Domain・Applicationから環境変数やHTTP Contextを参照しません。
- 日時計算はTemporalを使います。
- 業務上の失敗を識別する場合は共通の`DomainError`を使い、それ以外のエラー生成には通常の`Error`を使います。
  - 個別の失敗ごとに独自のエラークラスは作りません。
- 通常の成功経路を順に実行し、外部処理の失敗は元の例外を伝えます。
  - ログと応答への変換は入口で扱います。
    - ログ・URL・失敗応答には、秘密値・トークン・個人情報・利用者のコンテンツ・外部応答や例外の詳細を含めません。
    - 調査は問い合わせIDや対象のIDで照合します。
- 環境による具体実装の選択も入口で行い、Domainには環境判定を持ち込みません。
- モデルの型と振る舞いは[Zodモデルの記述](typescript.md#zodモデルの記述)に従います。

## Application

- 外部データの取得と時刻・乱数・IDの確定を担当し、Domainの判断・生成に必要な値を渡します。
  - Domainの処理に必須のモデルを取得できなければ、その処理を呼ばずに中止します。
  - 業務判断に使う時刻は、操作内で一度確定します。
- 複数モデルの生成呼び出しと保存の進行、トランザクション範囲を制御します。
  - モデルの境界とは別に、一体で保存すべき範囲を決め、Repositoryの操作とDBの仕組みで必要な原子性を保ちます。
- 操作は`src/application/<対象>/<対象>.ts`にまとめ、必要な操作を追加します。原則として操作ごとにファイルを分けません。
  - 例えば、Userの操作は`src/application/user/user.ts`にまとめます。
- 操作名はCRUD（作成・取得・更新・削除）を基本とし、画面や利用フロー名ではなく、対象データへの操作を表します。
  - 作成は`createX`、取得は既存に合わせて`findX`・`getX`、更新は`updateX`、削除は`deleteX`などを使います。
  - 既存データがあれば返し、なければ作成する操作は`findOrCreateX`など、実際の動作が分かる名前にします。
  - 送信などCRUDで表せない操作には、業務上の動詞を使います。
- 不要なCRUD操作や単純な中継関数は増やしません。

## Repository

- Repositoryのinterfaceは対象のDomain内の`*Repository.ts`に定義し、モデルのファイルとは分けます。
  - Senderなど外部との入出力を表すinterfaceも、対象のDomain内の専用ファイルに定義します。
- 契約・実装はUserやChannelなどのリソース単位でまとめ、操作やユースケースごとに別のRepositoryを増やしません。
  - 同じリソースの検索・作成などは、既存のRepositoryに追加します。
- 命名や構成をそろえる場合も、一体で保存すべき処理の原子性を保ちます。
  - すべての保存が成功するか、変更が残らないようにします。
- 単一参照は`find`、複数参照は`findMany`を基本名とします。
- 対象がない場合、単一参照・更新は例外、複数参照は空配列を返します。
- 取得値はZodで復元します。
- 名称と責務は既存の用語に合わせ、単純な中継関数や将来のためだけの抽象化は増やしません。

## DBスキーマ

- migrationのカラム定義はプロパティのアルファベット順の対象外とし、主キー、関連ID、業務上の主要な項目、日時の順に並べます。
  - 作成・更新日時は末尾に置きます。
