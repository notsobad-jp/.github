# テスト方針

毎回のCI待ち時間を開発の生産性コストとして扱い、必要最小限のテストを維持します。網羅率や件数を目標にせず、実装の追認・既存検証の重複・想定しない利用規模のテストを追加しません。

## 検証の分担

業務条件・入力境界・失敗時の処理順は、必要なものを単体テストで確認します。結合テストは実DBの制約・Repository・実行環境の接続など、単体では守れない重要な保証の代表ケースに絞ります。
テストは隔離したローカル環境と模擬外部応答を使い、本番環境・実外部サービスへ接続しません。具体的な環境と保証範囲は各リポジトリのREADMEを参照します。

## 追加・変更の判断

既存ケースへの統合・置き換えを先に検討し、別の環境の起動や同じフローの構成違いによる再実行を安易に増やしません。
テストを追加するときは、具体的に防ぐ不具合、既存テストでは不足する理由、実行時間と環境準備の追加コストをPRで説明します。結合テストの場合は、単体で代替できない理由も説明します。
各リポジトリで合意した保証範囲と許容リスクを維持します。削除した検証を一般的な安全性や将来の可能性だけで復活させません。
実際の障害や提供仕様の変更などで重要性が変わった場合は、防ぐ損失と毎回のCIコストを比較し、追加する最小の検証と保証範囲の変更を説明します。
