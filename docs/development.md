# 開発と変更の提出

## 既存方針と資料

既存の実装・規約に従います。既存例から判断できないルールは利用者に確認し、合意後に該当する規約へ追記します。
設計・提供仕様を変える場合は、同じ変更で対応するdocsも更新します。型・関数シグネチャ・処理順・設定値はコードと設定を正本とし、docsへ重複記載しません。
設計・提供仕様はdocs、議論の背景はDiscussion、残作業はIssue、変更とレビューはPRに置きます。
各リポジトリのAGENTS.mdには作業に応じた資料・スキルの参照先を置き、規約や手順の本文は参照先で管理します。

## 検証とpush

開発環境と検証コマンドは各リポジトリのREADMEを参照します。push前に送信するコミットで、結合テストを含む指定のCI一式が手元で成功することを確認します。
`pre-push`フックを有効にし、`--no-verify`・フックの無効化・検証の省略で回避しません。環境不足や失敗時はpushせず、原因を解消するか利用者へ不足を伝えます。
テストの選択・追加は[テスト方針](testing.md)に従います。

## PR

[共通PRテンプレート](../.github/pull_request_template.md)に従います。リポジトリに独自のテンプレートがある場合はそちらを使います。検証欄には、変更に応じて確認が必要と判断した点と理由、確認方法・結果を記載します。毎回必須のCI実行は本文へ定型記載しません。
画面を変更した場合は、変更後の表示が分かるスクリーンショットをPRやDiscussionに添付し、画面幅や表示状態を記載します。スクリーンショットは`docs`などのリポジトリ管理対象に保存しません。
