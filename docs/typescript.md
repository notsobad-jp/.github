# TypeScriptの記述とモデル

## 基本方針

- TypeScriptとZodで、常に不変条件を満たすモデルを扱います（always valid）。
- DDD・クリーンアーキテクチャ・関数型の考え方を使い、軽い構成を優先します。
- ルールは可能な限りBiomeと型で表現し、決定的に検査できるようにします。
  - 新しいルールを追加するときも、まずLintまたは型で表現できるか検討します。
  - この文書では、設定だけでは表せない設計判断や記述方法を補います。
- 型チェック・Lintの設定と導入方法は[共通パッケージ](../packages/config/README.md)を参照します。
- レイヤーの責務と依存は[構成とレイヤーの責務](architecture.md)に従います。

## 記述規約

- 型・interface・オブジェクト・JSONのプロパティはアルファベット順にします。
  - テスト・ドキュメントのコード例にも適用しますが、評価・上書きなど順序に意味がある場合はその意味を優先します。

## Zodモデルの記述

- この文書でモデルは、エンティティと値オブジェクトの総称とする。
- モデルはtypeと関数で表し、データはプレーンなオブジェクトや値として扱う。
- schemaを型の正本とし、公開モデルと型は同名にする。(companion object)
  - モデルの出力型は`z.infer`で取得する。
  - schema・型・振る舞いはモデルごとに同じファイルへまとめる。
- 値オブジェクトはエンティティとファイルを分け、所属するドメイン概念の配下に値オブジェクトごとのディレクトリと同名のファイルを置く。
  - 特定のドメイン概念に属さない共通の値オブジェクトは`src/domain/shared/`配下に同様に配置する。
- brand・readonly・振る舞いなどを付ける元のschemaを別定義にする場合は、`XSchema`と`X`のように名前を区別する。
- 作成用schemaは`XToCreate`のように用途で命名し、型が必要なら同名で定義する。
  - 公開範囲や型の定義有無だけを理由に`Schema`を付けない。
- 振る舞いはモデルを引数に取る名前付き純粋関数として別に定義し、`this`に依存させない。
  - モデルに対する操作は対象を第1引数に取り、呼び出し側では順に呼び出して途中の値に名前を付ける。
- 振る舞いがある場合は、定義済みのschemaと関数の参照を`Object.assign`でまとめ、モデル名で公開する。
  - 同名のcompanion objectとして、`Subscription.parse(input)`・`Subscription.create(input)`のように使う。
  - 関数の参照はプロパティの省略記法を使い、`Object.assign`内にschemaや関数の定義を書かない。
- 振る舞いがなければschemaをモデル名で公開する。
- オブジェクトモデルは公開時に`readonly()`を適用し、内部schemaは拡張可能に保つ。
  - 用途別schemaも内部schemaを再利用し、公開モデルの`unwrap()`を基本にしない。
- プロパティの許容値で表せる成立条件は、その値のschemaで定義し、推論型にも反映する。
- 通常は内部schemaと公開モデルの2段階にする。
  - `BaseSchema`などの中間定義は、複数schemaでの共通部分の再利用など、合成上の役割がある場合だけ設ける。
- Zod標準の検証はデフォルトのエラーメッセージを使う。
  - `refine`などの独自検証には検証内容に応じたメッセージを定義する。

### 不変条件と復元

- 基本schemaの`parse`は常に守る成立条件を検証し、保存済みモデルの復元にも使う。
- 作成・削除などの操作時だけの条件を復元時に再適用しない。
  - 新規作成に生成関数、復元に`parse`を使うことは、この規約によるAPIの使い分けとする。
- エンティティ本体にはbrandを付け、検証前のオブジェクトと型で区別する。
  - brandはDomainで定義し、Domainの`parse`や生成関数を通して付与する。
  - 値オブジェクトのbrandは、値の意味や検証済みであることを型で区別するため原則付ける。

### 作成用入力と生成

- CRUDの新規作成として扱うエンティティの生成は、Domainの明示的な生成関数を通す。
  - 基本名は`create`とし、`Campaign.createFeeds`のように複数のエンティティを一括生成する関数も認める。
  - 検証と固定値の補完だけで完結しても、新規作成の入口として生成関数を設ける。内部の処理が増えても呼び出し方を保つ。
  - 値オブジェクトは`parse`で生成でき、`create`を必須にしない。
  - 通常の新規作成フローがないモデルに、形式をそろえるためだけの生成関数を増やさない。
- 1件のエンティティを作る`create`は、検証済みの`XToCreate`型を受け取る。
  - Applicationが`XToCreate.parse`で項目・作成時の条件を検証し、固定値の初期値を補完する。
  - 作成用schemaは基本schemaを再利用し、作成時だけの条件を復元用の基本schemaから分ける。
  - 作成対象のデータ自体に対する条件を検証する。例えば、開始日が明日以降であることを検証する。
  - 現在日などの検証基準は入力で受け取り、検証後の作成用データからは除ける。
  - `XToCreate`のbrandと`readonly`で検証済みの作成用データを表す。完成モデル`X`のbrandは、この段階では付けない。
  - 検証前の値や復元したモデルを、`create`の入力型と互換にしない。
- 入力検証と生成の両方に時刻を渡す場合は、Applicationで一度確定した同じ値を使う。
- 検証済みの`XToCreate`型は`z.infer`で取得する。検証前の入力を型で表す場合は`z.input`を使い、補完・変換・brand付与の前後を区別する。
- 生成関数は、業務判断や組み立て後のモデルをschemaで検証し、完成モデルのbrandを付けて返す。一括生成でも各エンティティを検証する。

### 他のデータとの整合性

- 他モデルとの関係や既存データに基づく操作可否は、生成関数・操作関数内の明示的な処理で判断する。
  - 例えば、所有関係、プランによる制限、既存Channelの有無、既存予約との重複を判断する。
  - 判定に必要なモデルや時刻などの値は、[Application](architecture.md#application)が取得・確定して渡す。
  - 複雑な業務判断やモデルの組み立てを、schemaの`refine`・`transform`へ押し込まない。
- 厳密な一意性や同時更新への対策は、DBの制約・トリガー・トランザクションで担保する。
  - Domainの事前重複判定は分かりやすい業務エラーを返すためのものとし、同時実行の競合を防ぐ最終保証とは区別する。

### 操作と検証済みの型

- 業務判断・値の計算・固定した状態の組み立てを伴う操作は、明示的に呼び出す純粋関数で扱う。
  - 購読・解除などCRUDでは表せない操作には、`subscribe`・`unsubscribe`のように業務上の動詞を使う。
  - これらの操作は必要な値オブジェクトやモデルを受け取り、モデルを返す場合は結果をschemaで`parse`する。用途別の入力型・brandを一律に要求しない。
- 生成・操作関数の第1引数は主対象のモデルまたはデータとし、判断・組み立てに必要な他モデルや時刻などの追加材料は第2引数のオブジェクトにまとめる。
  - 追加材料が不要なら、第1引数だけにする。
- 属性の差し替えと基本schemaでの検証だけで完結する更新は、Applicationで差し替え後のモデルを`parse`して保存できる。
  - 単純な`parse`を中継するDomainの更新関数や、形式のためだけの用途別型は設けない。
- 操作条件を確認した既存モデルを後続へ引き継ぐ必要がある場合は、`XToDelete`のように用途を示すschemaと同名の型を用意する。汎用的な`ValidatedX`は避ける。
  - 基本schemaを再利用し、完成モデルのbrandを保った上で、確認した条件を用途のbrandで示す。作成前の入力型とは区別する。
  - 検証だけで完結する条件は、用途別schemaの`parse`で確認できる。他モデルとの関係も判断する場合はDomainの操作関数で可否を確認して結果を返し、結果のschemaは非公開にして型だけを公開できる。
  - 必要な他モデルや時刻などは入力で受け取り、出力には対象モデルの値だけを残す。操作時の条件を通常の復元へ混ぜない。
- 生成・操作の入口を表すもの以外は、単純な`parse`のラッパーやfactoryを増やさない。

- brandや用途別の型は検証した状態を引き継ぐための設計制約であり、セキュリティ境界ではない。
  - 操作用の入力を検証した型、操作条件を確認した既存モデル、操作後の完成モデルを区別し、その型が確認した条件を明確にする。
  - Domain外で安易にcastせず、取得後の同時更新や別の日・集約への流用まで保証したとは扱わない。
