# TypeScriptの記述とモデル

## 基本方針

- TypeScriptとZodで、常に不変条件を満たすモデルを扱います（always valid）。
- DDD・クリーンアーキテクチャ・関数型の考え方を使い、軽い構成を優先します。
- ルールは可能な限りBiomeと型で表現し、決定的に検査できるようにします。
  - 新しいルールを追加するときも、まずLintまたは型で表現できるか検討します。
  - この文書では、設定だけでは表せない設計判断や記述方法を補います。
- 型チェック・Lintの設定と導入方法は[共通パッケージ](../packages/config/README.md)を参照します。
- レイヤーの責務と依存は[構成とレイヤーの責務](architecture.md)に従います。

## 記述規約

- 型・interface・オブジェクト・JSONのプロパティはアルファベット順にします。
  - テスト・ドキュメントのコード例にも適用しますが、評価・上書きなど順序に意味がある場合はその意味を優先します。

## Zodモデルの記述

- この文書でモデルは、エンティティと値オブジェクトの総称とする。
- モデルはtypeと関数で表し、データはプレーンなオブジェクトや値として扱う。
- schemaを型の正本とし、公開モデルと型は同名にする。(companion object)
  - 型は`z.infer`で取得する。
  - schema・型・振る舞いはモデルごとに同じファイルへまとめる。
- 値オブジェクトはエンティティとファイルを分け、所属するドメイン概念の配下に値オブジェクトごとのディレクトリと同名のファイルを置く。
  - 特定のドメイン概念に属さない共通の値オブジェクトは`src/domain/shared/`配下に同様に配置する。
- 内部schemaはモデル名に`Schema`を付けて定義する。
- 振る舞いはモデルを引数に取る名前付き純粋関数として別に定義し、`this`に依存させない。
  - モデルに対する操作は対象を第1引数に取り、呼び出し側では順に呼び出して途中の値に名前を付ける。
- 振る舞いがある場合は、定義済みのschemaと関数の参照を`Object.assign`でまとめ、モデル名で公開する。
  - 同名のcompanion objectとして、`Subscription.parse(input)`・`Subscription.create(input)`のように使う。
  - 関数の参照はプロパティの省略記法を使い、`Object.assign`内にschemaや関数の定義を書かない。
- 振る舞いがなければschemaをモデル名で公開する。
- オブジェクトモデルは公開時に`readonly()`を適用し、内部schemaは拡張可能に保つ。
  - 用途別schemaも内部schemaを再利用し、公開モデルの`unwrap()`を基本にしない。
- プロパティの許容値で表せる成立条件は、その値のschemaで定義し、推論型にも反映する。
- 通常は内部schemaと公開モデルの2段階にする。
  - `BaseSchema`などの中間定義は、複数schemaでの共通部分の再利用など、合成上の役割がある場合だけ設ける。
- Zod標準の検証はデフォルトのエラーメッセージを使う。
  - `refine`などの独自検証には検証内容に応じたメッセージを定義する。

### 不変条件と復元

- 基本schemaの`parse`は常に守る成立条件を検証し、保存済みモデルの復元にも使う。
- 作成・削除などの操作時だけの条件を復元時に再適用しない。
- エンティティ本体にはbrandを付け、検証前のオブジェクトと型で区別する。
  - brandはDomainで定義し、Domainの`parse`や生成関数を通して付与する。
  - 値オブジェクトのbrandは、値の意味や検証済みであることを型で区別するため原則付ける。

### 作成用入力と生成

- エンティティの新規生成は、Domainの明示的な生成関数を通す。
  - 基本名は`create`とし、`Campaign.createFeeds`のように複数のエンティティを一括生成する関数も認める。
  - 値オブジェクトは`parse`で生成でき、`create`を必須にしない。
- 作成用入力は`XCreateInput`のように用途を示すschemaと同名の型で定義し、`z.infer`で取得する。
  - エンティティの内部schemaから必要な項目を`.pick`するなど、既存のschemaを再利用する。
  - 値オブジェクトや配列なども組み合わせ、完成形のエンティティからの派生に限定しない。
  - 入力自身に関する作成時だけの制約を`refine`などで定義し、`.brand()`で検証済みの入力型にする。
  - 現在時刻などの文脈が必要な場合は、`createInput(today)`のようにschemaを返す関数の引数で受け取る。
- `create`は検証済みの作成用入力を受け取り、ID・初期値・関連データなどからエンティティを組み立てる。
  - 現在時刻やID生成結果などの非決定的な値は、Applicationで確定して引数で渡す。
  - 組み立てた値は最後にエンティティのschemaで`parse`し、不変条件を満たすbrand付きの値を返す。一括生成でも各エンティティを検証する。
- 作成用入力のbrandは入力の作成条件を検証した印であり、完成形のエンティティや他データとの整合性まで検証した印ではない。
  - 例えば、開始日が明日以降であることは作成用入力、期間が1〜365日であることは期間の値オブジェクトの不変条件とする。
  - 入力と完成形の両方で同じ不変条件を検証してもよい。条件の定義はschemaで共通化する。

### 他のデータとの整合性

- 他のエンティティとの整合性を判断するルールはDomainの関数に置き、判定に必要なエンティティを引数で受け取る。
  - 例えば、同じChannelの配信期間が重複しないことは、生成関数が既存Campaignを受け取って判定する。
- Applicationは「データを集める → Domainの関数に渡す → 保存する」を担当する（Impureim Sandwich）。
- 厳密な一意性や同時更新への対策は、DBの制約やトランザクションで担保する。

### 操作と検証済みの型

- 値の計算や状態の変更を伴う操作は、明示的に呼び出す純粋関数で扱う。
  - エンティティの値を変更して返す場合も、結果をschemaで`parse`して不変条件を検証する。
- 削除などの操作条件を検証として表現できる場合は、基本schemaを再利用する用途別schemaと同名の型を用意し、`parse`する。
  - 必要な外部値は入力で受け取り、出力にはモデルの値だけを残す。
  - `XToDelete`のように用途を示し、汎用的な`ValidatedX`は避ける。
- 生成・操作の入口を表すもの以外は、単純な`parse`のラッパーやfactoryを増やさない。

- brandや用途別の型は検証した状態を引き継ぐための設計制約であり、セキュリティ境界ではない。
  - Domain外で安易にcastせず、取得後の同時更新や別の日・集約への流用まで保証したとは扱わない。
