# docsの書き方

## 書く内容

- 今後の実装で守る原則と、コードから分からない判断だけを書きます。
  - コードから分からない判断には、許容したリスク、意図して提供しないこと、規約から外れる理由などがあります。
- 実装の説明・設定値・作業履歴は書きません。具体的な値はコードと設定を正本にします。
- 確定した仕様だけを書き、変更前の仕様や実装との差分は併記しません。
- 1つの原則は1か所に書き、他の文書からはリンクします。

## 残す基準

- 記述を残すかは、その記述が消えたら、今後の別の実装で誰かが間違えるかで判断します。
- 実装が終わって完結した画面・文言・個別の判断は残しません。
- 初めて読む人が前後の文脈なしに意味を取れるように書きます。

## 文書の構成

- 文書は読む場面ごとに分け、関係のない作業で読む記述を混ぜません。
- 共通規約と同じ名前の文書には、その規約との差分だけを書きます。
  - 例えば、各リポジトリの`docs/testing.md`には、[テスト方針](testing.md)との差分を書きます。
- サービス固有の機能の文書には、その機能の仕様と設計をまとめます。
- リリースや機能公開までの暫定対応は、終了条件とともに`docs/interim.md`へ分けます。
  - 終了条件を満たしたら削除し、恒久的な方針は該当の文書へ移します。

## READMEとAGENTS.md

- READMEは人間向けに短く保ち、概要とセットアップ・ビルドに絞ります。
- AGENTS.mdには作業ごとの参照先を表で示し、各docsの入口にします。
- AGENTS.mdに書くのは、提出・デプロイなど作業の進め方の決まりだけとします。
  - 設計・仕様・検証の方針はdocsに書きます。
